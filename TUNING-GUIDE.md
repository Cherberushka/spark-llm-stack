## Шаг 1. Обновление компонентов (и конкретно LiteLLM — сейчас)

### 1.1. Матрица обновлений стека

| Компонент | Как обновляется | Частота | Риск / заметки |
|---|---|---|---|
| **LiteLLM** (`ghcr.io/berriai/litellm:main-stable`) | `docker compose pull litellm && up -d` | раз в 2–4 нед | метка плавающая! Перед pull тегнуть старый образ для отката; миграции БД стартуют сами |
| **Open WebUI** (`ghcr.io/open-webui/open-webui:main`) | `docker compose pull open-webui && up -d` | раз в 2–4 нед | плагин-совместимость редко ломается; бэкап тома перед major |
| **Caddy** (`caddy:2`) | `docker compose pull caddy && up -d` | раз в квартал | низкий |
| **Postgres/Redis** | не трогаем без причины | — | апгрейд мажора PG = отдельная процедура (pg_dump/restore) |
| **Движок Qwen3.8 (llama.cpp)** | пересборка `scripts/03b...` из master | по необходимости | следить за совместимостью DFlash2; после пересборки — `05-verify` |
| **GGUF-веса / кванты** | `hf download` нового файла + правка юнита | редко | тест A/B в Arena перед заменой боевого кванта |
| **Ollama + bge-m3** | переустановочный скрипт + `ollama pull bge-m3` | раз в квартал | низкий |
| **DGX OS (драйвер/CUDA)** | `apt full-upgrade` + reboot | по регламенту NVIDIA | сверять с версией драйвера, на которой валидированы рецепты (580.x) |
| **AnythingLLM (десктоп)** | встроенный апдейтер / новый installer | по желанию | воркспейсы переживают обновление; эмбеддер не сбрасывается |
| **Pi** | `pi update` | раз в 2–4 нед | конфиг `models.json` переживает |

Правило фазы эксплуатации: **обновляем по одному компоненту за окно**, после
каждого — `sudo bash scripts/05-verify.sh` (регресс-тест) и запись в журнал
обновлений (дата, компонент, старая→новая версия, результат).

### 1.2. Обновление LiteLLM — процедура (выполнять на Spark)

```bash
cd /home/user/spark-llm-stack/stack

# 0) зафиксировать текущую версию и ОТТЕГИРОВАТЬ образ для отката
sudo docker inspect spark-litellm --format '{{.Config.Image}} {{.Image}}' | tee /tmp/litellm-current
sudo docker tag "$(sudo docker inspect spark-litellm --format '{{.Image}}')" litellm-rollback:prev
curl -s http://127.0.0.1:4000/v1/models -H "Authorization: Bearer $(sudo grep -oP '(?<=^LITELLM_MASTER_KEY=).*' /etc/spark-llm.env)" | jq -r '.data[].id'

# 1) бэкап БД (ключи, пользователи, spend-логи)
sudo mkdir -p /root/backup
sudo docker exec spark-litellm-db pg_dump -U llmadmin litellm | gzip | sudo tee /root/backup/litellm-pre-update-$(date +%F-%H%M).sql.gz > /dev/null
ls -lh /root/backup/ | tail -2

# 2) новый образ + пересоздание
sudo docker compose pull litellm
sudo docker compose up -d litellm        # open-webui не трогаем: depends_on действует только при старте

# 3) дождаться миграций Prisma и health
for i in $(seq 1 90); do C=$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:4000/health/liveliness); [ "$C" = 200 ] && break; sleep 2; done; echo "health: $C"
sudo docker logs spark-litellm --tail 40 | grep -iE 'migrat|prisma|startup complete|version'

# 4) регресс
sudo bash /home/user/spark-llm-stack/scripts/05-verify.sh
# версия видна в UI (логин-страница/футер) и в логах; запишите в журнал обновлений
```

**Откат** (если миграция/поведение сломались):
```bash
cd /home/user/spark-llm-stack/stack
sudo sed -i 's|image: ghcr.io/berriai/litellm:main-stable|image: litellm-rollback:prev|' docker-compose.yml
sudo docker compose up -d litellm
# БД при необходимости: gunzip -c /root/backup/litellm-pre-*.sql.gz | sudo docker exec -i spark-litellm-db psql -U llmadmin litellm
```
После стабилизации новой версии: вернуть `main-stable` в compose и удалить тег
отката (`sudo docker rmi litellm-rollback:prev`), когда следующий апдейт пройдёт.

**Пины на будущее (Шаг 8):** после успешного окна замените в compose плавающую
метку на конкретную (`ghcr.io/berriai/litellm:<тег-версии>`, список тегов:
`https://github.com/BerriAI/litellm/pkgs/container/litellm`) — обновления
станут явным действием, а не «само приехало».

## Шаг 2. Кэш ответов и лимиты (экономия токенов на шлюзе)

Redis уже поднят — включаем кэш повторяющихся запросов (регенерации отчётов,
однотипные вопросы сотрудников):

```yaml
# stack/litellm/config.yaml → litellm_settings:
litellm_settings:
  cache: true            # redis-бэкенд подхватится из REDIS_HOST/PORT/PASSWORD
  # cache ttl по умолчанию 600 c; продлить: cache_params: {ttl: 3600}
```
```bash
sudo docker compose restart litellm
```
Эффект: идентичные запросы (те же messages+параметры) отвечаются из кэша за ~0
токенов. Логи кэша: UI → Logs (пометка cached).

Аудит лимитов: UI → Virtual Keys — у каждого ключа `rpm/tpm/max_budget`;
сервисным ключам (cron-отчёты) ставьте tpm повыше, человеческим — rpm 20–40.
Командные бюджеты: Teams → budget (в USD для локальной модели = 0, но лимиты
токенов работают).

## Шаг 3. AnythingLLM: зрение, агенты, «руки», скиллы, Astra

### 3.1. Зрение (computer vision)
AnythingLLM прокидывает прикреплённые изображения в OpenAI-совместимый чат,
если модель vision-capable — наш `qwen3.8-27b` именно такой (mmproj поднят на
движке). Проверка: в чате скрепка → скриншот/фото → «опиши/извлеки текст».
Если изображения не уходят (старая сборка AnythingLLM) — обновите приложение;
fallback: те же картинки прекрасно ест Open WebUI и Pi.

### 3.2. Агентный режим и встроенные скиллы
В чате AnythingLLM агент вызывается через **@agent** (или переключатель
режима). Набор скиллов управляется: *Настройки экземпляра → Навыки агента*
(Agent Skills): включить нужное, выключить лишнее (каждый скилл = инструменты
в промпте = лишние токены):
- **web-scraping / search** — только если нужен внешний веб (в клинике обычно нет);
- **file operations** — чтение/запись файлов воркспейса;
- **SQL agent** — подключение к БД (read-only строка подключения к МИС!);
- **summarization / chart generation** — полезно для отчётных задач.
Скиллы действуют **только в агент-вызове**, обычный чат = RAG по воркспейсу.

### 3.3. «Управление ПК» — через MCP, не через скиллы
Управление компьютером (файлы/процессы/оболочка станции) в AnythingLLM
появляется через **MCP-серверы**: *Настройки → MCP Servers* → добавить stdio-
сервер, например:
- `@wonderwhy-er/desktop-commander` — файлы + shell на **той машине, где стоит
  AnythingLLM** (ваша станция, не Spark!);
- `@modelcontextprotocol/server-filesystem` — только доступ к папкам (безопаснее).
Команда вида `npx -y @wonderwhy-er/desktop-commander` (нужен Node на станции).
После подключения в агент-чате появляются инструменты «выполни команду»,
«прочитай/запиши файл» — это и есть «управление ПК» с подтверждением действий.
**Безопасность:** MCP-shell даёт модели shell на станции — включайте только на
машинах разработчиков, только с подтверждением команд, никогда на общих ПК.

### 3.4. Можно ли поднять Pi внутри AnythingLLM?
**Нет.** Pi — терминальный харнесс (своя TUI, сессии, LSP, steer), он не
плагин и не MCP-сервер из коробки. Правильное разделение ролей:
- **Pi** — серьёзный код/репо/долгие агентные прогоны (терминал, IDE-расширения);
- **AnythingLLM** — документы/воркспейсы/десктоп-чат с локальными папками + MCP-руки;
- **Open WebUI** — общий веб-вход для организации, серверный RAG, админка.
Все три ходят в один шлюз и делят одни ключи/логи. Экзотика: MCP-сервер-обёртка
над `pi -p ...` технически возможна, но даёт худший UX, чем сам Pi.

### 3.5. Astra и выбор векторной БД
**Astra (DataStax AstraDB)** в списке векторных БД AnythingLLM — это **облако**:
ваши документы уходят за периметр. Для клиники — **нет**. Локальные варианты:
- **LanceDB** (встроен по умолчанию) — файлы лежат в профиле приложения, ноль
  настройки, достаточно для персональных воркспейсов. **Серверного режима в
  open-source нет** (только Cloud/Enterprise), поэтому синхронизации между
  рабочими станциями он не даёт — это личный блокнот, не общий корпус;
- **Chroma** — живёт внутри Open WebUI Knowledge, отдельного сервера не требует;
- **Qdrant self-hosted** — отдельный контейнер, нужен только при большом корпусе.

**Решение по организационному корпусу принято и обосновано замерами** — см.
`RAG-SCALE-PLAN.md`. Коротко: rag-svc переведён на v2 (векторы непрерывным файлом,
гибрид BM25+dense, фильтры по метаданным, `/stats`), и в этом виде держит все 777
действующих КР Минздрава (~105 000 фрагментов) на гибридном запросе ~0.1 с.
**Решением заказчика от 28.10.2026 поисковый движок Qdrant включается до массового
импорта всех КР** (рост корпуса к сценарию S2 ≈ 195k фрагментов, ночной импорт
параллельно с дневными запросами, дешёвое переключение на малом корпусе).
Переключение — одна строка env (`RAG_BACKEND=qdrant`), потому что SQLite остаётся
источником правды, а Qdrant — пересобираемым индексом; откат `--rollback` мгновенный.
Машинные пороги в `/stats` (≥200 000 фрагментов или p95 > 500 мс) после перехода
остаются контрольными точками мониторинга.

Итог по AnythingLLM: оставляем LanceDB как личный воркспейс; общий организационный
RAG — rag-svc (доступ агентам через MCP), интерактивный чат-RAG — Open WebUI Knowledge.

### 3.6. Настройка эффективности (чек-лист AnythingLLM)
- Эмбеддер: **bge-m3 через шлюз** (уже сделано; после смены — переиндексация).
- Context window: 32768 (чат) / 65536 (документные воркспейсы), потолок 131072.
- Chunking: дефолт или ~800–1200 токенов для плотных КР.
- Top-k в настройках воркспейса: 4–6 (больше = медленнее и шумнее).
- Temperature: 0.2–0.5 для извлечения фактов, 0.7–1.0 для черновиков.
- Один воркспейс = одна тема (не свалка): КР-терапия, КР-хирургия, Регламенты…
- Тяжёлые PDF со сканами: сначала OCR на сервере (`ocrmypdf`), потом в воркспейс.

## Шаг 5. Скорость и потребление токенов (системно)

**Базовая линия** (повторять после каждого изменения):
```bash
sudo bash scripts/05-verify.sh          # tok/s теста + все smoke-тесты
curl -s http://127.0.0.1:8000/metrics -H "Authorization: Bearer $(sudo grep -oP '(?<=^VLLM_API_KEY=).*' /etc/spark-llm.env)" | grep -E 'tokens_predicted|tokens_per_second' | head -5
```
Рычаги (по убыванию эффекта):
1. **Thinking off по умолчанию** (уже: `--reasoning-budget 0`) — главный
   сберегатель: −40–60% токенов в агентных циклах. Включать точечно.
2. **DFlash2-спекуляция** (уже включена) — ×1.8–2.5 к скорости декода;
   следите за accept-rate в метриках llama.cpp (`llama:spec_...`), при просадке
   ниже ~0.6 проверить версию llama.cpp/драфтера.
3. **Кэш шлюза** (Шаг 2) — повторяющиеся запросы бесплатны.
4. **Дисциплина контекста на клиентах**: окна 32–64K вместо «максимум»,
   чистка истории, top-k 4–6. Префилл 100K+ токенов = минуты простоя движка.
5. **--parallel**: при очереди из 2–3 одновременных агентов поднять до 2–4
   (`--parallel N` в юните qwen38-llamacpp; ctx делится на слоты: 160K/4=40K —
   достаточно большинству сессий). Один слот = максимальная скорость одному.
6. **KV-квантование** (`--cache-type-k/v q8_0`) — если упрётесь в память при
   больших ctx/parallel; цена ~1–2% качества внимания.
7. **Ночные batch-задачи** (конвертация, отчёты) — в окно 00:00–06:00 cron'ом,
   днём движок пуст людям.
8. Спекуляцию контролируйте метриками ПОСЛЕ трафика: `llamacpp:spec_decode_num_accepted_tokens_total`
   / `..._drafted_tokens_total` (acceptance rate 0.6–0.9 — норма; 0 при нулевом
   трафике сразу после рестарта — это норма, не поломка).
9. Наблюдение: `/ops` (KV%, running/waiting), LiteLLM Usage (токены по ключам),
   nvtop (память пула). Триггеры беспокойства: KV>85% постоянно, waiting>0
   подолгу, accept-rate спекуляции <0.6.

## Шаг 6. Скиллы и инструменты харнессов (курированно!)

Правило гигиены: описание каждого скилла/инструмента попадает в системный
промпт КАЖДОГО запроса. 8 курированных скиллов ≈ 1 КБ индекса; полный репозиторий
mattpocock (~40) = 5–6 КБ + шум выбора. Поэтому ставим минимум и ревизуем квартал.

### 6.1. Pi: курированный набор скиллов

```bash
# на рабочей станции разработчика (или на Spark для серверного Pi):
scp user@192.168.11.251:spark-llm-stack/scripts/10-install-pi-skills.sh .
bash 10-install-pi-skills.sh            # user-level: ~/.pi/agent/skills
FULL=1 bash 10-install-pi-skills.sh     # если осознанно хочется всё
```
Курированный состав: code-review, diagnosing-bugs, tdd, research, to-spec,
implement, handoff, writing-for-agents + taste-skill (фронтенд-вкус; требует
Node 22+ и Chrome для браузер-проверки). Проверка: в сессии Pi спросить
«какие скиллы доступны?» — модель читает индекс `~/.pi/agent/skills`.

### 6.2. MCP-набор по ролям (матрица)

| Роль | MCP-серверы | Где описано |
|---|---|---|
| Сотрудник/аналитик (AnythingLLM) | filesystem (корни = папки документов) | WINDOWS-MCP-GUIDE §3.1 |
| Разработчик (станция) | filesystem (репо) + desktop-commander **в песочнице-учётке** | §3.2, §10 |
| Разработчик (Pi) | тот же набор через `%USERPROFILE%\.pi\agent\mcp.json` | §5 |
| Отчётность по МИС | server-postgres **read-only** (после шага 4.3) | §3.3 |
| Сервер Spark | без MCP: серверные задачи = cron + print-режим Pi | WORKSTATIONS |

### 6.3. Open WebUI: гигиена Tools/Functions

- Tools привязываются к группам, а не «всем»: Text-to-SQL (шаг 4.3) — только
  «Администрация»/«Разработка»;
- системные промпты групп — короткие и императивные (цитаты, «нет в документах —
  так и скажи», черновик-для-проверки);
- Pipelines не включаем, пока нет реальной потребности (каждый пайплайн =
  задержка на каждый запрос).

### 6.4. Квартальная ревизия

1. Pi: просмотреть истории сессий — какие скиллы вызывались; невызыванные удалить.
2. AnythingLLM: тумблеры Agent Skills — то же правило.
3. Open WebUI Tools/Groups: отвязать неиспользуемое.
4. MCP: серверы, к которым не подключались за квартал — отключить (они стартуют
   на каждый агент-запрос = лишние секунды и токены на описание инструментов).

## Шаг 8. Политика обновлений и журнал

- Раз в месяц «окно обновлений» (30–60 мин): LiteLLM → Open WebUI → (квартал:
  Caddy, llama.cpp, DGX OS).
- Перед окном: бэкапы (том webui + pg_dump), тег-откат образов.
- После: `05-verify` + прогон золотого набора RAG + запись в журнал:
  `дата | компонент | было → стало | verify | заметки`.
- Плавающие метки заменяем пинами после первого успешного цикла (compose:
  теги версий; llama.cpp: git tag/commit в юните комментарием).
