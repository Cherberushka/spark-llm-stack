## 2. Архитектура агентной сети (топология «звезда» с оркестратором)

```
   Приём задач: Open WebUI Tool «Новая задача» · веб-форма · cron · API
                          │
              ┌───────────▼────────────┐
              │  ОРКЕСТРАТОР (Spark)   │  systemd-сервис (Python/Node)
              │  planner: qwen3.8 xhigh│  декомпозиция → граф подзадач
              │  router: реестр карточек агентов (имя, навыки, ключ, SLA)
              │  state: Postgres tasks_db (статусы, артефакты, события)
              │  gates: approvals человеком (prod-БД, публикация, деньги)
              │  budget: лимиты токенов/времени на задачу и на проект
              └─┬─────┬─────┬─────┬────┘
    key=docs    │     │     │     │  key=reports
        ┌───────▼┐ ┌──▼──────┐ ┌──▼────────┐ ┌▼────────────┐
        │DOC     │ │DB       │ │CODE       │ │REPORT       │
        │worker  │ │worker   │ │worker     │ │worker       │
        │RAG-Any │ │postgres │ │Pi headless│ │шаблоны+SQL  │
        │+OCR/md │ │MCP (ro) │ │+Graft+    │ │+humanizer-  │
        │+doc-   │ │+headroom│ │codebase-  │ │ free отчёт   │
        │skills  │ │ proxy   │ │memory MCP │ │              │
        └────────┘ └─────────┘ └───────────┘ └─────────────┘
   у каждого: свой виртуальный ключ LiteLLM, свой workspace-каталог,
   свой набор MCP, свой журнал событий; между собой НЕ общаются —
   только через оркестратор (аудируемость, отсутствие скрытых цепочек)
```

Принципы:
1. **Звезда, не меш**: worker'ы не вызывают друг друга напрямую. Любая
   передача артефакта — через оркестратор (запись в tasks_db + ссылка на
   файл в общем хранилище /srv/agents/artifacts). Плюс: полный аудит, минус:
   оркестратор — единая точка отказа (лечится systemd-рестартом и идемпотентностью задач).
2. **Агент = ключ + workspace + MCP-набор + карточка в реестре**. Карточка:
   имя, назначение, входы/выходы, запрещённое, стоимость (токены/мин), SLA.
   Router выбирает по карточкам, planner — по декомпозиции. Паттерн взят из
   agency-agents, реализация — своя таблица `agents_registry`.
3. **Одна модель, разные режимы**: planner/gate-анализ — thinking xhigh;
   worker-шаги — thinking off (скорость/токены); ревью — medium.
4. **Headroom-прокси** для db/code worker'ов: их tool-выводы (дампы, логи,
   pg_get_serdef) сжимаются до попадания в контекст — экономия до 60–90% токенов
   на больших проектах. Ставится на Spark: :4001 → LiteLLM :4000.
5. **Идемпотентность задач**: у каждой задачи `idempotency_key`; повторный
   прогон не дублирует артефакты; упавший worker перезапускается оркестратором
   с последнего чекпоинта (события в tasks_db).

### 2.1. Реализация оркестратора (P1, без нового фреймворка)

- Сервис: Python (FastAPI) или Node; systemd-юнит `agents-orchestrator`;
  порт только loopback, наружу — маршрут Caddy `/tasks` (UI: минималистичный
  дашборд задач в стиле /ops).
- Хранилище: отдельная БД Postgres `agents_tasks` (контейнер litellm-db уже
  есть — новая база в том же сервере, либо отдельный контейнер; проще — та же).
- Приём: Open WebUI Tool `create_task(template, payload)` + REST + cron-задачи.
- Planner: один вызов qwen3.8 (xhigh) → JSON-граф подзадач (схема фиксирована:
  steps[{agent, input_refs, output, gate?}]); валидация схемы кодом, не моделью.
- Dispatcher: запускает worker'ов: doc/db/report — внутренние исполнители
  (Python-функции + MCP-клиенты); code — `pi --profile headless`-процесс с
  workspace-каталогом задачи; каждый прогон пишет события (start/step/artifact/fail).
- Gates: задача с флагом `gate: human` останавливается до решения в UI
  (approve/reject с комментарием); журнал gates — часть аудита.

## 3. MCP: что это и как настроено у нас

**MCP (Model Context Protocol)** — JSON-RPC протокол «агент ↔ сервер
инструментов»: сервер объявляет tools/resources/prompts; клиент (харнесс)
вызывает их с подтверждениями. Транспорты: **stdio** (сервер = локальный
процесс харнесса) и **streamable HTTP** (удалённый сервер). Ценность: N агентов
× M инструментов без N×M интеграций; граница безопасности задаётся сервером
(какие корни/БД/команды он вообще готов обслуживать).

**Топология у нас**: MCP-серверы — «органы чувств/руки» worker'ов; оркестратор
сам MCP не вызывает (он планирует), кроме read-only справочных (реестр схем БД).

### 3.1. Матрица MCP-серверов сети

| MCP-сервер | Транспорт | Кто потребляет | Граница |
|---|---|---|---|
| postgres-ro (МИС, prod) | stdio/HTTP на Spark | db-worker, report-worker | read-only пользователь, только SELECT, statement_timeout, список схем |
| postgres-staging (копия БД) | stdio на Spark, изолированная сеть | db-project-worker (P5) | DDL разрешён; прод недоступен из этого контейнера |
| filesystem: /srv/kb-inbox, /srv/agents/artifacts, /srv/reports-out | stdio | doc-worker, report-worker | только эти корни |
| filesystem: репо-mirror /srv/repos/* | stdio | code-worker | только mirror, не оригиналы |
| codebase-memory-mcp или Graft | stdio | code-worker, db-project-worker | индекс репо/PL-SQL-кода |
| RAG-Anything API (обёртка-MCP) | HTTP loopback | doc-worker, Open WebUI Tool | чтение индексов корпуса |
| headroom (не MCP, прокси) | HTTP | db/code worker'ы → LiteLLM | сжатие tool-выводов |
| desktop-commander / filesystem станции | stdio на станции | AnythingLLM/Pi разработчика | песочница-учётка (WINDOWS-MCP-GUIDE §10) |

### 3.2. Правила развёртывания MCP

1. Серверы, нужные нескольким worker'ам, живут **на Spark** как systemd-юниты
   (stdio-серверы оборачиваются в `mcp-proxy`/supergateway в HTTP) — один
   процесс на всех, единые логи и границы.
2. Станционные MCP (filesystem станции, commander) остаются stdio внутри
   харнесса станции — серверные данные туда не спускаются.
3. У каждого MCP-сервера — свой системный пользователь Linux и свой каталог;
   секреты (DSN) — в EnvironmentFile 600, не в аргументах процесса.
4. Версии MCP-серверов пинятся (npm-пакеты с точным тегом), обновление — в
   ежемесячное окно (TUNING-GUIDE шаг 8).
5. Ни один MCP не публикуется наружу org-подсетей; HTTP-варианты — loopback +
   маршрут Caddy только при реальной необходимости и с basic_auth.

## 4. Контроль и наблюдение за задачами и проектами

### 4.1. Три контура наблюдения

| Контур | Источник | Что видно |
|---|---|---|
| Задачи/проекты | tasks_db оркестратора + UI `/tasks` | статусы шагов, артефакты, gates, сроки, перезапуски |
| Токены/стоимость | LiteLLM Usage (ключ = worker) | расход по агентам/задачам/отделам, аномалии (задача съела 5× нормы) |
| Инфраструктура | /ops, nvtop, метрики llama.cpp | KV%, очереди, tok/s, память пула |

### 4.2. Регламент контроля

- **Утренний digest** (cron 07:30): сводка за сутки — задачи по статусам, топ-5
  по токенaм, ошибки worker'ов, открытые gates. Куда: файл + сообщение в
  Open WebUI-чат админов (Tool-уведомление) или email при настроенном SMTP.
- **Бюджеты задач**: у шаблона задачи норма токенов/времени; превышение ×2 →
  задача паузится + алерт админу (защита от зациклившихся агентов).
- **Gates обязательны** для: любых записей в прод-БД (даже через staging-перенос),
  публикации документов наружу группы, удаления/перемещения файлов вне
  artifacts, задач с budget>порога.
- **Аудит**: события задач (JSONL) + логи LiteLLM + история чатов Open WebUI —
  хранение ≥6 мес; раз в квартал выборочный ручной разбор 10 задач.
- **Kill-switch**: `systemctl stop agents-orchestrator` останавливает приём и
  диспетчеризацию; worker'ы доживают текущий шаг; экстренно — `docker stop`/
  `pkill -f pi` по тегу задачи.

### 4.3. Лёгковесные агенты для рядовых пользователей

Рядовому пользователю (врач, регистратор) **не нужен агентный харнесс**: его
«лёгкий агент» уже есть — **Open WebUI чат + Knowledge** (RAG без инструментов)
плюс **шаблоны задач оркестратора** (кнопки/формы): «месячный отчёт по приёмам»,
«конвертировать этот скан в справку», «выписка по пациенту-черновик» (с gate
врача!). Форма → оркестратор → worker'ы → результат в чат с цитатами/таблицей.

Если «лёгковесного не хватает» (пользователь просит произвольные действия) —
**не** выдаём свободные инструменты, а расширяем набор шаблонов: потребность
= сигнал добавить шаблон с фиксированным пайплайном и gate'ом.

### 4.4. Ограничения оркестратора для простых пользователей (да, необходимы)

1. **Allowlist шаблонов** по группам (group → templates); свободная постановка
   задачи доступна только группам «Разработка»/«Администрация».
2. **Нет прямых инструментов**: у пользовательских сессий Open WebUI нет
   Tools/MCP вообще; все действия — через задачи оркестратора с фикс-пайплайном.
3. **Gate по классу действия**: чтение/черновик — авто; публикация/запись/
   деньги/персданные — человек-approver из группы-владельца процесса.
4. **Бюджеты**: tpm/rpm на групповой ключ LiteLLM + норма токенов на шаблон.
5. **Периметр данных**: шаблон видит только свои источники (список БД-схем/
   баз Knowledge в карточке шаблона); перекрёстного доступа нет.
6. **Журнальность**: каждая пользовательская задача пишется в аудит с автором.

## 5. Пайплайны предметных линий

### 5.1. Обработка документов (P2)

```
ВХОД (три пути):
  a) шара doctor / kb-inbox / веб-форма → cron 5 мин → задача doc-convert (по одному файлу)
  b) scripts/19-import-clinrec.sh → массовый импорт каталога (прогноз → пилот → прогон)
  c) scripts/13-add-doc.sh → один файл + сразу контрольный вопрос

КОНВЕРТАЦИЯ:
  pdf с текстовым слоем → pdftotext -layout        (дешевле, GPU не нужен)
  pdf-скан              → pdftoppm 150dpi → VLM-OCR нашей же Qwen3.8-27B (vision)
                          fallback: ocrmypdf rus+eng (на русских сканах хуже)
  docx/odt/rtf/html     → pandoc → gfm

ИНДЕКС (rag-svc v2):
  chunk 900/150 → bge-m3 (1024d) → vectors.f32 (непрерывный массив, слоты переиспользуются)
                                 → index.db (текст + метаданные) + chunks_fts (BM25)
  метаданные: title, specialty, nosology, mkb10, doctype, version, valid_from,
              superseded_by, current, source_path, sha256, ocr

ПОИСК:
  hybrid = BM25 (префиксный, под русскую морфологию) + dense, слияние RRF
         + фильтры (specialty/doctype/mkb10) + current=1 по умолчанию
         + порог релевантности RAG_MIN_SCORE (нерелевантное → честное «не найдено»)

ВЫХОД:
  оркестратор doc-qa · Open WebUI Tool · MCP-сервер для любых агентов (kb_search и др.)
  → ответы с цитатами (документ + версия); артефакты MD в /srv/agents/artifacts
```
- Конвейер = cron/инотайт на kb-inbox + worker «docs» для задач «конвертируй этот
  файл»; массовый импорт идёт МИМО оркестратора (иначе 777 КР = 777 задач и мусор
  в журнале), но в тот же индекс.
- Версионирование: имя = `ТЕМА_ОРГ-ГОД-ММ_vN`. Прежняя редакция НЕ удаляется, а
  помечается `POST /supersede {"current":false}` — в выдачу по умолчанию не попадает,
  но остаётся для аудита «чем руководствовались в марте».
- RAG-Anything (графовый разбор таблиц/формул) остаётся апгрейдом P2b: он не отменяет
  ничего выше, а надстраивается. Обоснование отложено — см. RAG-SCALE-PLAN.md §8
  (сначала качество чанкинга на реальном корпусе, потом графы).
- Масштабирование до всех КР Минздрава (777 док. ≈ 105k фрагментов) измерено:
  ~0.1 с на гибридный запрос, ~740 МБ на диске. **Решение 28.10.2026: Qdrant
  включается до массового импорта** — процедура и порядок: **RAG-SCALE-PLAN.md §4.2**,
  переключение — `scripts/18-vector-store-qdrant.sh` (откат `--rollback`, SQLite —
  источник правды).

### 5.2. Большой проект: анализ и оптимизация БД (триггеры/процедуры) (P5)

Фазы под управлением оркестратора (каждая — задача с gate'ами):
1. **Снятие копии**: pg_dump прод → restore в postgres-staging (контейнер,
   изолированная сеть; персданные по возможности маскингом).
2. **Аудит**: db-project-worker собирает каталог объектов (pg_proc/pg_trigger),
   pg_stat_statements, планы EXPLAIN ANALYZE типовых нагрузок; codebase-memory/
   graphify строят граф вызовов процедур/триггеров (кто кого, горячие пути).
3. **Гипотезы**: planner выдаёт список кандидатов (дублирующиеся триггеры,
   SARG-нелогики, курсоры, отсутствующие индексы, N+1 в процедурах) с оценкой
   эффекта/риска; человек утверждает шорт-лист (gate).
4. **Проверка на staging**: code-worker (Pi headless) пишет миграцию + тесты;
   прогон нагрузочного сценария до/после (pgbench/типовые запросы), метрики в
   артефакты; ревью-агент (code-review skill) + gate DBA.
5. **Отчёт и rollout-план**: report-worker собирает документ (что, зачем,
   метрики до/после, план отката); gate руководства; перенос в прод — руками
   DBA по плану (агент в прод не пишет).
6. **Пост-контроль**: неделя мониторинга pg_stat_statements в проде человеком;
   откат по плану при регрессе.

### 5.3. Объяснение «на пальцах»: агентная сеть и MCP

- **Агентная сеть** = оркестратор (планирует и распределяет) + разнородные
  worker'ы (умеют действия: документы, БД, код, отчёты) + общая шина
  инструментов (MCP) + память/состояние (tasks_db, индексы) + контур контроля
  (ключи, логи, gates, бюджеты). От «просто чата с моделью» отличается наличием
  состояния, действий и ответственности за результат по шагам.
- **MCP** = «USB-C для инструментов»: единый протокол, которым любой харнесс
  (Pi, Cline, AnythingLLM, dsh, наши worker'ы) подключает любые серверы
  инструментов (БД, файлы, браузер, графы кода) без самописных интеграций.
  Сервер MCP = граница безопасности (что в принципе можно), харнесс = граница
  решения (что сделать сейчас, с подтверждением человека где нужно).
- Почему звезда с оркестратором, а не «все со всеми»: управляемость (один
  аудиторский след), предсказуемость бюджетов, простота отключения одного
  worker'а; цена — оркестратор как единая точка управления (не данных).

## 7. Ролевая специализация внутри линий (паттерн everything-claude-code, портированный на локальный стек)

### 7.0. Провенанс источников
- Оригинал: `affaan-m/everything-claude-code` (ECC) — живая библиотека
  конфигов (agents/skills/commands/hooks/rules) для Claude-Code-семейства.
- `worldflowai/everything-claude-code` — замороженная январняя копия-клон
  (один push); её не использовать (устаревшие промпты, риск squat-правок).
- ECC не устанавливается как есть (он под Claude Code/Codex); **портируются
  паттерны**: роли-карточки, чек-листы gate'ов, хуки «тесты обязательны»,
  research-first.

### 7.1. Экономика мультиагентности на одном локальном движке
- Роль = (системный промпт + набор скиллов + набор MCP + gate + бюджет), а не
  отдельный процесс/модель. Переключение ролей бесплатно; ценность даёт
  **разделение контекстов**: reviewer не наследует bias реализатора, handoff
  между ролями = сжатая выжимка, а не 200K переписки.
- Цена каждой роли-сессии = повторный prefill контекста репо; лечится общим
  индексом (Graft / codebase-memory-mcp) и артефактными handoff'ами.
- Параллельность ограничена слотами движка (2): параллельно пускаем только
  независимые ревью-потоки (reviewer ∥ security-reviewer); остальное — цепочкой.
- Рoster ограничен здравым смыслом: 6–8 ролей на кодинг-линию, 3–4 на DB-линию.
  «64 агента» из ECC — это каталог персон под облачные модели с бесконечным
  параллелизмом; локально такой каталог = раздувание реестра без выгоды.
- Один агент достаточен (router выбирает композицию по классу задачи):
  правка ≤1 файла, опечатки, конфиги — оверхед ролей больше пользы.

### 7.2. Реестр ролей кодинг-линии

| Роль | Thinking | Инструменты/MCP | Gate/бюджет |
|---|---|---|---|
| planner/architect | xhigh | read-only fs, Graft/codebase-graph, research | план = артефакт; утверждает человек для крупных задач |
| implementer | off | fs+shell воркспейса задачи, тесты обязательны (хук ECC-паттерна) | автотесты зелёные, иначе шаг не закрыт |
| qa/test-writer | low | fs+shell, tdd-скилл | покрытие новых веток |
| reviewer | medium | read-only diff, code-review-скилл | вердикт + список замечаний (блокирует merge-артефакт) |
| security-reviewer | medium | read-only, чек-лист (инъекции, секреты, зависимости) | параллелен reviewer'у |
| docs-writer | off | fs, writing-for-agents | обновление AGENTS.md/README задачи |

Композиции: feature = planner→implementer→qa→(reviewer ∥ security)→docs;
hotfix = implementer→reviewer; refactor = planner→implementer→qa→perf-check.

**Статус реализации (29.10.2026).** Диспетчер оркестратора исполняет роли
`implementer`/`qa`/`reviewer`/`security` через Pi headless (worker `pi`,
`agents/orchestrator/orchestrator.py::w_pi`): запуск от `agent-dev`
раннером `/usr/local/sbin/agent-run-pi.sh`, рабочая копия репозитория
`/srv/agents/repos/<repo>`, ветка `task-<id>`, артефакты `TASK-*.md`/`OUT-*.md` и
`task-<id>-<role>.diff` (пишется всегда: база задачи, счётчики, ошибки git, новые
неотслеживаемые файлы — материал человеческого гейта). git зовётся от владельца репозитория
(`sudo -n -u agent-dev`, fallback — разовый `-c safe.directory`): оркестратор работает от
root, и git ≥ 2.35 на чужой репо отвечает `dubious ownership` с пустым stdout (v3.12.5).
Шаблоны: `code-fix` (implementer→qa→reviewer→гейт человека), `code-review`
(security→reviewer→гейт), `code-feature` (planner→…→гейт). Роль получает
выводы предыдущих ролей (артефактный handoff, а не перенос контекста),
reviewer/security дополнительно — `git diff` от базы задачи (ревизия на старте шага, а не
`HEAD`: иначе коммит роли оставил бы гейт без дифа). Вердикт парсится из вывода:
нет явного PASS/APPROVE — шаг не считается принятым. Параллельность ролей
пока не включена: диспетчер однопоточный, один шаг = один сеанс Pi
(P4.1: живые логи шагов, cancel, параллельные reviewer ∥ security).
Graft/codebase-memory-mcp не подключены — цена повторного prefill контекста
репо остаётся; лечится ограничением размера задач и handoff'ами.

### 7.3. Роли DB-линии (для P5 и отчётности)
auditor (схемы/статистика, read-only), perf-analyst (EXPLAIN/pg_stat, staging),
migration-writer (DDL-скрипты + тесты на staging, gate DBA), report-writer
(числа только из SQL-артефактов).

### 7.4. Где живут роли
- В оркестраторе: таблица `agents_registry` (карточка роли = промпт-шаблон +
  skills-подмножество + MCP-список + gate + бюджет) — dispatcher стартует
  Pi headless-сессию с параметрами роли;
- В IDE/терминале человека: те же роли как скиллы Pi/Cline («действуй как
  reviewer») — для интерактивной работы;
- В ECC заимствуем готовые чек-листы ролей (перевод/адаптация под Qwen3.8 и
  наш стек), а не их число.

## 8. Специфика MSSQL (МИС) и чек-лист входных данных

### 8.1. Что учтено в дизайне под MS SQL Server
- Диалект T-SQL в промптах/шаблонах: `TOP (n)` вместо LIMIT, `[квадратные]`
  идентификаторы, `GETDATE()/DATEDIFF()/FORMAT()`, оконные функции, `SET
  TRANSACTION ISOLATION LEVEL READ UNCOMMITTED` НЕ используем (только
  read-only-пользователь + `GRANT SELECT`);
- Драйверы на Spark: `pymssql` (arm64-колёса) или `pyodbc` + MS ODBC Driver 18
  (arm64-пакет msodbcsql18 для Ubuntu 24.04 существует); выбор — pymssql как
  более лёгкий, pyodbc — если нужны features драйвера (Azure AD и т.п.);
- Read-only контур: логин БД с `GRANT SELECT` на разрешённых схемах + `DENY`
  на всё остальное; statement-timeout через `SET LOCK_TIMEOUT`;
- MCP для MSSQL: собственный тонкий stdio-обёрточник (~60 строк, pymssql +
  whitelist-схем) — вместо сторонних пакетов: полный контроль границ и логов;
  появится в P3 вместе с Text-to-SQL Tool;
- Большие дампы (планы, dm_*) прогоняем через headroom-прокси до попадания в
  контекст worker'ов.

### 8.2. Чек-лист: что передать администратору БД (для P3 и P5)
1. **Доступ**: хост/порт/имя экземпляра SQL Server; версия (SELECT @@VERSION);
   тип аутентификации (SQL / Windows AD); доступность с IP Spark (тест
   `Test-NetConnection`/`nc`); нужна ли заявка на открытие порта в файрволе.
2. **Read-only логин**: имя предлагаемого логина (напр. `spark_ro`); список
   схем/таблиц/представлений для отчётов (2–10 имён + бизнес-смысл каждого);
   готовый GRANT-скрипт подписать у DBA:
   `CREATE LOGIN spark_ro WITH PASSWORD=...; CREATE USER spark_ro FOR LOGIN spark_ro;
    GRANT SELECT ON SCHEMA::dbo TO spark_ro;  -- и нужные схемы`
3. **Словарь данных**: есть ли описание таблиц/полей (документация МИС,
   extended properties) — файл/выгрузка для загрузки в RAG-базу «Словарь БД».
4. **Ограничения периметра**: какие таблицы/поля категорически запрещены
   (персданные пациентов и т.п.) — внесём в DENY и в карточку db-роли.
5. **Для P5 (оптимизация триггеров/процедур)**: возможность снять копию БД
   (backup/restore) на изолированный staging-экземпляр; окно для снятия копии
   и частота обновления; политика маскирования персданных в копии; контакт DBA
   для gate'ов; регламент переноса изменений в прод (кто применяет миграции).
6. **Метрики базы**: включён ли Query Store / pg-аналог (sys.dm_exec_query_stats
   доступны всегда); право read-only на dm_* представления.
7. **Часовой пояс и collation** сервера (влияет на шаблоны отчётов по датам).

### 8.3. Статус фаз

## 9. Порядок фаз: DB-линия откладываема (решение 27.10.2026)

P3/P5 не находятся на критическом пути агентной сети разработки:
- рекомендуемый порядок: **P1 → P2 → P4 (кодинг-сеть) → P6 → P3 → P5 → P7**;
- чек-лист §8.2 администратору БД отправить **сразу параллельно** (бумажный
  цикл GRANT/staging — самый длинный lead-time); P3 подключается по готовности доступа;
- предохранитель P1: роли db-линии и report сидятся с `active=false`
  (таблица agents_registry), planner их не видит, диспетчер отклоняет задачи,
  их требующие, с явной причиной «роли не развёрнуты»; включение в P3:
  `update agents_registry set active=true where role in ('db-auditor','db-perf','db-migration','report');`
- если задачам разработки нужна живая БД до P3 — два безопасных паттерна:
  (а) read-only DSN на **dev/staging-копию** внутри песочницы code-worker'а
  (секрет в env песочницы, не в репо); (б) замороженный словарь схемы в репо
  (`docs/db-schema.md` из выгрузки sys.tables/sys.columns) — хватает для
  написания кода против МИС без живого доступа. Прод не трогаем до P3.
