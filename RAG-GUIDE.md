# RAG для частной клиники — подробный гид (с нуля)

Как работает поиск по документации в нашем стеке, какие документы загружать,
как обновлять базу при изменении клинических рекомендаций (КР) и как держать
качество. Привязка к стеку: эмбеддинги **bge-m3** (Ollama :11434, через шлюз
LiteLLM) + **Open WebUI Knowledge** (векторное хранилище и поиск встроены).

---

## 1. Что такое RAG — простыми словами

LLM знает только то, чему её научили до даты отсечения знаний, и **не знает
ваших внутренних документов**. RAG (Retrieval-Augmented Generation, «генерация
с подмешиванием найденного») решает это без дообучения модели:

```
 Документы клиники                Вопрос пользователя
      │                                │
      ▼                                ▼
 1. Нарезка на чанки            2. Тот же эмбеддер (bge-m3)
    (~500–1000 слов)                   │
      │                                ▼
      ▼                        3. Поиск по векторной БД:
 1a. Эмбеддинги bge-m3             top-5..10 похожих чанков
    (векторы 1024 dim)                 │
      │                                ▼
      ▼                        4. Чанки подмешиваются в промпт
  Векторный индекс ────────────►    + вопрос пользователя
 (Open WebUI Knowledge)              │
                                     ▼
                             5. Qwen3.8-27B отвечает ПО НАЙДЕННОМУ,
                                со ссылками на документы (citations)
```

Ключевые следствия, которые надо понять сразу:

- **Качество ответа = качество поиска.** Модель не может процитировать то, что
  поиск не нашёл. Поэтому подготовка документов (§4) важнее выбора модели.
- **Эмбеддинг-модель одна на всю базу.** bge-m3 понимает 100+ языков (русский
  и английский кросс-лингвально: вопрос по-русски найдёт англоязычный фрагмент
  и наоборот). Смена эмбеддера = полная переиндексация базы.
- **RAG отвечает на «что написано в документах».** Для «сколько у нас приёмов
  за сентябрь» нужен не RAG, а Text-to-SQL к базе данных (§8).
- Ответы всегда должны сопровождаться **цитатой источника** — в Open WebUI это
  включается; без цитат доверять ответу в медицине нельзя.

## 2. Open WebUI Knowledge — как устроено

*Knowledge* (Knowledge Bases) — встроенный RAG-контур Open WebUI: своё
векторное хранилище (по умолчанию Chroma внутри контейнера), нарезка,
эмбеддинг, гибридный поиск (векторы + ключевые слова), опциональный reranker.

**Базовая настройка (один раз, в админке):**

1. *Admin Panel → Settings → Documents (RAG)*:
   - **Embedding engine**: OpenAI-compatible → base URL уже прописан в контейнер
     (`http://litellm:4000/v1`), модель **`bge-m3`** — укажите её в
     *RAG Embedding Model* (env `RAG_EMBEDDING_MODEL=bge-m3` мы уже задали).
   - **Chunk size / overlap**: старт — 800 / 150. Для длинных КР можно 1000/200.
   - **Hybrid search** — включить; **Reranker** — на росте добавить
     `bge-reranker-v2-m3` (см. §7).
   - **Citations** — включить отображение источников в ответах.
2. *Workspace → Knowledge → Create*: создайте базы по разделению доступа (§5):
   например `Клинические рекомендации`, `Внутренние SOP`, `Регламенты и приказы`,
   `Лекарственный справочник`.
3. Загрузите файлы (PDF, DOCX, TXT, MD, CSV; поддерживается загрузка по URL).
   Open WebUI сам нарежет и проиндексирует — прогресс виден в интерфейсе.
4. Привяжите базу к чату: в чате *+# Attach Knowledge Base*, либо к модели —
   тогда она доступна всем, кто этой моделью пользуется.

**Повседневное использование:** сотрудник открывает чат, прикрепляет нужную
базу (или база уже привязана к модели) и спрашивает: «Тактика ведения пациента
с ХОБЛ при обострении по нашим КР — кратко, со ссылкой на раздел». Ответ
приходит с кликабельными цитатами из загруженных документов.

## 3. Какие документы загружать (для частной клиники)

| Категория | Примеры | Формат/подготовка |
|---|---|---|
| **Клинические рекомендации** | КР Минздрава по профилям клиники, стандарты медпомощи | PDF с текстового слоя (не скан!); сканы → OCR (§4) |
| **Внутренние SOP/протоколы** | маршрутизация пациента, протоколы процедур, алгоритмы дежурств | DOCX/PDF; один документ = одна тема |
| **Шаблоны и формы** | шаблоны осмотров, выписок, согласий, отчётов | DOCX/MD — модель будет использовать их как образцы при составлении отчётов |
| **Лекарственный справочник** | инструкции ЛП, формулярный список, взаимодействия | структурированные PDF/CSV |
| **Регуляторика** | приказы МЗ, лицензионные требования, 152-ФЗ/PHI-политики, порядок оказания помощи по профилю | PDF |
| **Организационное** | регламенты работы отделений, инструкции к МИС, график/правила записи | DOCX/PDF |
| **Прайс и услуги** | перечень услуг с описаниями | для «что входит в услугу» — RAG; для цен/остатков/статистики — **БД** (§8) |

**Что НЕ загружать в общие базы:**
- **Персональные данные пациентов** (карты, выписки с ФИО) — в общую базу
  знаний нельзя: Knowledge доступна всем, у кого есть доступ к чату. Обезличенные
  случаи/деперсонизированные выборки — можно, с согласия юриста.
- Операционные данные (расписание, остатки, финансы) — они живут в БД и
  устаревают в RAG мгновенно.
- Устаревшие версии документов (§6 — главная причина «галлюцинаций по бумаге»).

## 4. Подготовка документов (80% качества RAG)

1. **Только текстовый слой.** Скан без OCR = мусор в индексе. Проверяется так:
   выделите текст в PDF мышью — не выделяется → нужен OCR. Инструменты:
   Docling (IBM, отлично держит таблицы), Tesseract+ocrmypdf (`ocrmypdf --language rus+eng in.pdf out.pdf`), FineReader.
2. **Таблицы → markdown/CSV.** RAG плохо ищет внутри «сырых» PDF-таблиц.
   Ключевые таблицы (дозы, тарифы, нормативы) выносите в CSV/MD или хотя бы
   убеждайтесь, что OCR сохранил структуру.
3. **Один документ — одна тема.** Сборник «всё обо всём» на 400 страниц ищется
   хуже, чем 20 файлов по темам.
4. **Имя файла = метаданные.** Конвенция:
   `КР_Артериальная_гипертензия_МЗ-2026_v2.pdf`,
   `SOP_Приём_педиатра_2026-03_v1.docx`. По имени персонал и модель понимают
   версию и дату.
5. **Заголовок и дата внутри.** Первая страница: название, утверждён (кем/когда),
   версия, дата следующего пересмотра.
6. **Удаляйте «шум»**: титульные листы с подписями, пустые страницы, водяные
   знаки — они попадают в чанки и мешают поиску.

## 5. Доступы (админка Open WebUI)

- **Группы**: например `Врачи`, `Регистратура`, `Администрация`. Каждой группе —
  свои Knowledge-базы и свои модели (*Admin → Users/Groups*).
- Базы «для всех» (КР, SOP) vs «для руководства» (регламенты, финансы) —
  разделяются именно группами.
- **Журнал**: *Admin → Logs* хранит запросы — кто что спрашивал (аудит).
- После заведения всех учётных записей: `ENABLE_SIGNUP=false` в `stack/.env` →
  `docker compose up -d`.

## 6. Обновление при изменении клинических рекомендаций — регламент

Это самый важный процесс: **устаревшая КР в базе опаснее её отсутствия.**

**Источники изменений (поставить на мониторинг):**
- Рубрикатор КР Минздрава (cr.minzdrav.gov.ru) — обновления по профилям;
- рассылки/телеграм-каналы профильных профсообществ;
- правовые системы (Консультант/Гарант) — приказы и порядки;
- внутренний регламент: ответственный (например, начмед или клинический
  фармаколог) + частота ревизии (рекомендую: еженедельная проверка рубрикатора,
  ежеквартальный полный аудит базы).

**Порядок действий при выходе новой версии КР (ручной, 5–10 минут):**
1. Скачать новый документ, переименовать по конвенции:
   `КР_ХОБЛ_МЗ-2026-10_v3.pdf`.
2. *Knowledge → нужная база → Add file* — загрузить новую версию.
   Дождаться окончания индексации (статус в интерфейсе).
3. **Старая версия** — по-разному для двух индексов:
   * *Knowledge Open WebUI*: **удалить из индекса** (версионирования там нет,
     устаревшая копия будет всплывать в цитатах). Архив — в файловой папке `/archive`.
   * *Корпус rag-svc (организационная база)*: **НЕ удалять**, а пометить устаревшей:
     ```bash
     curl -s -X POST http://127.0.0.1:8502/supersede -H 'Content-Type: application/json' \
       -d '{"name":"kr_hobl_2023","by":"kr_hobl_2026","current":false}'
     ```
     В выдачу по умолчанию она больше не попадает (`RAG_CURRENT_ONLY=1`), но остаётся
     для аудита «чем руководствовались в марте 2024-го» — для клиники это юридически
     значимо. В ответе агента такая редакция помечается `[УСТАРЕВШАЯ РЕДАКЦИЯ]`.
4. **Проверка контрольными вопросами** (§6.1) — убедиться, что ответы
   ссылаются на новую версию.
5. Записать в журнал обновлений: дата, документ, кто загрузил, какие вопросы
   проверены. (Журнал — обычный MD-файл в репозитории документов.)

### 6.1 «Золотой набор» контрольных вопросов

Держите 15–30 вопросов по ключевым КР с эталонными ответами/разделами,
например:
- «Первая линия терапии при впервые выявленной АГ?» → ждём ссылку на КР v3, раздел 4.
- «Периодичность спирометрии при ХОБЛ?» → новая норма из свежей КР.
После каждого обновления прогоняйте их в чате — если ответ цитирует старый
документ, индексация не завершилась или старая версия не удалена.

### 6.2 Автоматизация обновления (на рост)

У Open WebUI есть API для Knowledge (создание баз, загрузка файлов —
`/api/v1/knowledge/...`, ключ админа в *Settings → Account*). Схема:
1. Папка на сервере `/data/kb-inbox/` (расшарена для ответственного).
2. Cron-скрипт: новый файл → API-загрузка в соответствующую базу → уведомление
   в чат/почту → после подтверждения человека → удаление старой версии по
   маске имени.
Полностью автоматическое удаление старых версий не рекомендую — шаг
подтверждения человеком защищает от случайной потери документа.

## 7. Качество и рост (когда база вырастет)

Симптом → действие:

| Симптом | Что делать |
|---|---|
| Ответы «не находит в документах», хотя текст есть | Увеличить top-k поиска; проверить OCR/текстовый слой; уменьшить chunk size до 500 |
| Находит не тот раздел (похожие формулировки) | Включить **reranker** (bge-reranker-v2-m3 через TEI-контейнер или настройки Open WebUI); добавить метаданные в имена файлов |
| Путает версии документов | Строже регламент §6: в Knowledge — удалять старое немедленно; в корпусе rag-svc — `POST /supersede` (не удалять, а выводить из выдачи). В промпте базы — «цитируй только действующие редакции» |
| Корпус растёт: сотни и тысячи документов | Qdrant включается **до** массового импорта всех КР (решение 28.10.2026) — `scripts/18-vector-store-qdrant.sh`, откат `--rollback`. Контроль после перехода: `curl -s localhost:8502/stats \| jq '{backend,chunks,p95_ms:.query_latency_ms.p95,recommendation}'` (p95 > 500 мс на qdrant — повод смотреть ресурсы/HNSW). Замеры sqlite-альтернативы и методика: **RAG-SCALE-PLAN.md** |
| Много одновременных пользователей | Для rag-svc v2 латентность от числа пользователей почти не зависит (на запрос выделяется ~0.4 МБ, а не ~500 МБ). Для Open WebUI Knowledge — ограничение контейнера, а не индекса |
| Нужны сложные пайплайны (парсинг сканов, извлечение таблиц) | Скан-ветка уже на VLM-OCR (Qwen3.8-27B vision), а не на tesseract — на русских сканах точнее. Таблицы/формулы: Docling или RAG-Anything (апгрейд P2b), оригиналы хранить в `/srv/agents/kb-inbox` и в бэкапе |
| Ищет по общему слову, но не по точному термину | Это лексическая ветка. В rag-svc v2 гибрид уже включён (`RAG_QUERY_MODE=hybrid`); проверьте `mode=bm25` и `mode=dense` отдельно, чтобы понять, какая ветка виновата. Редкий термин не находится → добавить в глоссарий `/srv/agents/glossary.md` |
| Отвечает общими словами вместо «в корпусе этого нет» | Поднять `RAG_MIN_SCORE` (калибровка — RAG-SCALE-PLAN.md §7.3). Для медицинской базы честное «не найдено» ценнее правдоподобной цитаты |
| Ответы без ссылок | Проверить включение Citations в RAG-настройках; в системном промпте базы — «всегда указывай документ и раздел» |

**Оценка качества (делайте раз в квартал):** прогон «золотого набора» (§6.1) +
20 реальных вопросов от сотрудников; метрика простая: доля ответов, где
источник корректен и достаточен. Цель ≥90%.

## 8. Граница RAG ↔ БД (важно для отчётов)

| Вопрос | Инструмент |
|---|---|
| «Тактика при обострении ХОБЛ по нашим КР?» | **RAG** |
| «Составь месячный отчёт по приёмам/выручке» | **Text-to-SQL к МИС/БД**: модель пишет SQL → сервис исполняет (read-only пользователь!) → модель оформляет отчёт по шаблону из Knowledge |
| «Сколько стоит услуга X?» | **БД** (цены меняются; в RAG устареют) |
| «Что входит в услугу X (описание)?» | **RAG** (прайс-описания) |

В Open WebUI это реализуется инструментами/функциями (*Workspace → Tools*):
Python-функция с подключением к БД (read-only), которую модель вызывает через
tool calling. Числа в отчётах должны приходить из результата SQL, а не из
«памяти» модели — это правило №1 анти-галлюцинации для клиники.

## 9. Медицина и безопасность — обязательные рамки

1. **Решение принимает человек.** RAG-ответ — справочная черновая выборка из
   документов, не медицинское назначение. В системный промпт баз добавить:
   «Ответ носит справочный характер, решение принимает лечащий врач; всегда
   приводи цитату документа и раздел».
2. **ПДн не покидают периметр**: весь стек локальный (Spark в вашей серверной),
   интернет нужен только для обновлений. Доступ к веб-интерфейсу — по учёткам
   и через VPN/LAN, не в белый интернет (§12 runbook).
3. **Аудит**: логи запросов Open WebUI + логи LiteLLM (кто, какая модель, когда)
   — храните ≥6 месяцев.
4. **Регламент инцидента**: нашли ошибочный/устаревший ответ → фиксация →
   правка документа/индекса → повторный прогон контрольных вопросов.

## 9a. Загрузка файлов: все способы

| Способ | Кто | Куда |
|---|---|---|
| Веб-форма в дашборде `https://<IP>/tasks/` (кнопка «Загрузить») | IT/админ | сразу в kb-inbox + опционально задача doc-convert |
| API `POST /api/inbox` (multipart, X-Orch-Key) | скрипты/интеграции | kb-inbox + задача |
| Сетевая папка `\\\\192.168.11.251\\kb-inbox` (Samba) | сотрудники сами | kb-inbox (задачу ставит чат/Open WebUI) |
| Общая папка `\\\\192.168.11.251\\doctor` (scripts/15): `_incoming` → авто-задача doc-convert каждые 5 мин, `_results` → готовые .md | отдел (группа doctor) | полный цикл без IT |
| `scp`/`cp` на сервер | IT | kb-inbox |
| **`scripts/19-import-clinrec.sh` — массовый импорт каталога** (сотни документов: прогноз стоимости → пилот `--limit 20` → прогон `--ocr never` → сканы ночью `--night-only`) | IT | `/srv/kb/clinrec/<специальность>/` → напрямую в индекс rag-svc, минуя оркестратор |
| **MCP-инструменты `kb_search` / `kb_list_docs` / `kb_doc_chunks` / `kb_stats`** — чтение корпуса любым агентом (Pi, dsh, свой код) | агенты | `agents/mcp/rag-mcp-server.py` (stdio) |

Через **чат Open WebUI бинарник в задачу передать нельзя** (Tools принимают только
текстовые параметры) — чат создаёт задачи по ИМЕНИ файла, лежащего в inbox.

**Массовый импорт идёт мимо оркестратора намеренно**: 777 КР через задачи doc-convert —
это 777 задач, шагов и событий в Postgres плюс часы ожидания. `rag_bulk_ingest.py` пишет
в тот же индекс напрямую, ведёт журнал по sha256 (resume после Ctrl-C/обрыва), показывает
прогноз стоимости ДО старта и умеет ночное окно, чтобы VLM-OCR не отбирал GPU у врачей.
Порядок действий и модель стоимости — **RAG-SCALE-PLAN.md §6**.

## 10. Чек-лист запуска RAG (первая неделя)

- [ ] В админке: embedding = bge-m3, chunk 800/150, hybrid search on, citations on
- [ ] Созданы базы: КР / SOP / Регламенты / Лекарства (по группам доступа)
- [ ] Загружено 10–20 самых используемых документов (текстовый слой проверен)
- [ ] Группы и пользователи заведены, signup выключен
- [ ] «Золотой набор»: 15 контрольных вопросов, первый прогон — ≥80% корректных
- [ ] Назначен ответственный за обновления, заведён журнал обновлений
- [ ] Персонал обучен: как прикреплять базу, как читать цитаты, куда сообщать об ошибках
